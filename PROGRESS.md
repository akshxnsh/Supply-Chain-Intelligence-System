## Step 10 - Redis cache on the read endpoints (branch step-13-api-cache, 2026-11-11)
- `src/dashboard/cache.py`: `@cached(group, ttl)` for GET endpoints (sync and async). - **Connection-pool finding:** the pool did a health-check round trip before EVERY query. It now trusts a connection verified in the last 30 s (`DB_CHECK_AFTER_IDLE_S`, 0 = old behaviour), which lowers each uncached request (numbers below).
- **Measured** (`python -m scripts.benchmark_api`; real uvicorn over HTTP on localhost; DB = Neon Singapore from this laptop; Redis = local Docker; 60 sequential requests per endpoint after a cold first request, freshness 20; `docs/benchmarks/api_cache.md`):
| endpoint | A: no cache, old pool check p50 / p95 | B: no cache, new pool check p50 / p95 | C: Redis cache hit p50 / p95 |
|---|---:|---:|---:|
| suppliers | 383 / 414 ms | 321 / 415 ms | 5.1 / 7.2 ms |
| alerts (legacy) | 384 / 484 ms | 319 / 402 ms | 5.3 / 6.7 ms |
| risk alerts (new) | 404 / 470 ms | 324 / 407 ms | 5.0 / 7.8 ms |
| freshness (6 queries) | 439 / 775 ms | 355 / 644 ms | 4.5 / 6.8 ms |
  Concurrent (8 threads x 15 mixed requests): A 18 requests/s, B 24 requests/s, C 384 requests/s (p95 528 / 414 / 45 ms).
- How to read this honestly: (1) the cache win is large (about 60-80x at p50) because the database is remote and slow (each query is about 300 ms from here); with a local database the uncached time would be a few ms and the benefit small. (2) C is the steady state: every request after the first was a hit (hit rate 100% in this test by construction); a real hit rate depends on traffic and the TTLs. (3) The price is staleness up to the TTL for changes made outside the API (the risk pipeline writes alerts without calling the API), cleared immediately for changes made through the API.
